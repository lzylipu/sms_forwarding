# 代码审查报告 / Code Review Report

> 版本：2.1.5 · 审查范围：`code/` 全部 27 个文件、5,573 行 · 方法：逐模块通读 + 不变量核对 + 真机复现
>
> 本文档记录这一轮审查发现的全部缺陷、根因、修复方式与验证证据。写在仓库里是为了不留「口头承诺」：每条结论都能对着代码和测试复现。

## 一、为什么"移植现有功能"还会出这么多问题

这份固件不是从零写的，是把上游能跑的实现搬过来、再改造成「免 IDE、单文件、可真配网、现代 UI」的形态。问题集中爆发有三个具体原因，不完全是运气：

1. **上游没有测试，也没有写下来的不变量。** 例如"`modemPump()` 是唯一读串口的地方"、"PDU 必须先入库再走策略"这类约束只存在于实现里。改造时一旦新增一条调用路径（管理短信命令 → `sendSMS` → `atExec` → 再次 `modemPump`），约束就被无声破坏，编译器也不会提醒。

2. **改造动了三个全局假设，连带作废了一批旧逻辑。**
   - 认证从 HTTP Basic 改成 Cookie 会话 → 所有"顺便蹭 Basic 鉴权"的路径（文件上传回调、扫描接口）失去保护；
   - 打包从"多分片"改成"单一整包" → 设备端识别整包的判据（按文件大小）失效；
   - 渲染从一次性 `sendContent` 大字符串改成分块 + 占位符替换 → 分块边界处理不当就会漏字面量。

3. **我自己的自测覆盖的是"我改的那条路径"，不是全部入口。** 改完 OTA 打包只验证了"整片刷写能启动"，没验证"网页 OTA 上传同一个文件"；改完认证只验证了"页面能登录"，没验证"上传接口有没有被保护"。这类遗漏靠单点测试永远发现不了，只能靠入口清单 + 逐条回归。

结论：这类项目必须有一份"入口清单"（每个 HTTP 接口、每条 AT 调用、每个状态机迁移）并逐条跑，而不是只跑主流程。

### 自测中发现的两条

第 18、19 条不是读代码看出来的，是**照着"用户会怎么把设备弄失联"去实测**才暴露的：先故意存一个不存在的 SSID，设备当场掉线并卡在配网热点里。第 18 条是我新写的兜底逻辑，第 19 条是我第一版兜底的实现缺陷——写的时候只想到"失败就换一组"，没想过 WiFi 驱动在 connecting 状态下会拒绝改配置。修完重新加了一个不存在的 SSID 再跑一遍，设备 40 秒内自己回到原网络。

这两条正好说明为什么"跑通了"不等于"没漏洞"：功能路径正确、逻辑分支错误，只有真机走一遍异常路径才会现形。

## 四、仍然存在的已知限制（未修，明确写出来）

这些不是遗漏，是有意留在这个版本之外，避免在收尾阶段引入更大风险：

1. **推送与 SMTP 是同步的**：一条短信的推送仍会占用主循环最多数秒（重试时更长）。短信不会因此丢失（PDU 已队列化，串口持续被读取），但此期间网页交互会变慢。
2. **`sendSMS` 是同步的**：最坏情况约 35 秒（`CMGS` 等待 30 秒），网页上表现为请求慢，不会阻塞短信接收。
3. **没有 CSRF token**：依赖 `HttpOnly + SameSite=Lax` Cookie，跨站 POST 不会携带会话；设备设计为局域网内使用，未加独立 token。
4. **`ssl_client.setInsecure()`**：HTTPS 推送不校验证书，换取体积与内存。若推送目标被劫持，内容可能泄露。
5. **管理短信命令只有 `SMS:` 与 `RESET`**。
6. **模组能力上限**（硬件，非软件问题）：无语音/无 USSD/无 GNSS/无 AT 级定位/`AT+CLAC` 不支持/`AT+MCHIPINFO="temp"` 返回 -1。

## 五、给自己定的回归清单

以后只要动到下列任何一项，必须跑完整回归（`tests/` 与真机脚本）：

- 认证 / 会话 → 页面登录、所有接口 401、上传接口保护

- 推送 → 每种通道各发一条测试消息
